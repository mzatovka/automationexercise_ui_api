# AutomationExercise UI + API Tests

Автоматизированное тестирование веб-приложения **Automation Exercise** с использованием UI- и API-тестов.

Проект демонстрирует автоматизацию основных пользовательских сценариев интернет-магазина: регистрация и авторизация пользователя, работа с товарами и корзиной, оформление заказа, проверка категорий товаров, поиск товаров, а также взаимодействие с REST API.

**Repository:** `mzatovka/automationexercise_ui_api`

**Application:** https://automationexercise.com/

---

# Реализованные UI Test Cases

## TC1 — Register User

**Цель:** проверить регистрацию нового пользователя.

Основные проверки:

1. Открытие главной страницы.
2. Переход на `Signup / Login`.
3. Заполнение имени и уникального email.
4. Создание аккаунта.
5. Заполнение персональных данных.
6. Выбор пола.
7. Заполнение пароля.
8. Работа с выпадающими списками.
9. Подписка на newsletter.
10. Заполнение адреса.
11. Создание аккаунта.
12. Проверка сообщения `ACCOUNT CREATED!`.
13. Удаление созданного аккаунта.
14. Проверка сообщения `ACCOUNT DELETED!`.

Тест помечен маркером `critical`.

---

## TC2 — Login User

**Цель:** проверить авторизацию зарегистрированного пользователя.

Проверяется:

* переход на страницу авторизации;
* ввод email;
* ввод password;
* успешный login;
* переход на главную страницу;
* наличие `Logout`;
* выход из аккаунта;
* переход обратно на `/login`.

Для подготовки пользователя используется API-фикстура `register_user_api`, что позволяет не проходить регистрацию через UI перед каждым тестом.

## TC3 — Login with Incorrect Email/Password

**Цель:** проверить обработку некорректных credentials.

Используются неверные:

* email;

Проверяется отображение соответствующего сообщения пользователю.

**Цель:** проверить корректный выход из аккаунта.

## API-тестирование

Для автоматизации API-тестов используется библиотека **Requests** совместно с **Pytest**.

В проекте реализовано **7 API-тестов**, которые покрывают позитивные и негативные сценарии работы с API:

1. **Получение списка товаров** — `GET /productsList`

   * проверка HTTP-статуса `200`;
   * проверка наличия товаров в ответе;
   * получение ID первого товара.

2. **Проверка неподдерживаемого метода** — `POST /productsList`

   * проверка `responseCode = 405`;
   * проверка сообщения `This request method is not supported.`

3. **Поиск товара** — `POST /searchProduct`

   * передача параметра `search_product`;
   * проверка HTTP-статуса `200`;
   * проверка, что название каждого найденного товара содержит искомое значение.

4. **Поиск товара без обязательного параметра** — `POST /searchProduct`

   * запрос выполняется без параметра `search_product`;
   * проверка `responseCode = 400`;
   * проверка сообщения об отсутствии обязательного параметра.

5. **Авторизация с валидными данными** — `POST /verifyLogin`

   * проверка HTTP-статуса `200`;
   * проверка сообщения `User exists!`.

6. **Авторизация с невалидными данными** — `POST /verifyLogin`

   * проверка `responseCode = 404`;
   * проверка сообщения `User not found!`.

7. **Создание пользователя** — `POST /createAccount`

   * передача данных нового пользователя;
   * динамическое формирование email;
   * проверка `responseCode = 201`.

### Покрываемые API endpoints

| Метод  | Endpoint         | Назначение                        |
| ------ | ---------------- | --------------------------------- |
| `GET`  | `/productsList`  | Получение списка товаров          |
| `POST` | `/productsList`  | Проверка неподдерживаемого метода |
| `POST` | `/searchProduct` | Поиск товаров                     |
| `POST` | `/verifyLogin`   | Проверка авторизации              |
| `POST` | `/createAccount` | Создание пользователя             |

Таким образом, API-тесты покрывают работу с товарами, поиск товаров, авторизацию пользователей, создание пользователей, а также негативные сценарии с некорректными запросами.


# Fixtures

В проекте реализован отдельный файл `fixtures.py`.

Используются следующие основные фикстуры:

### `create_browser`

Создаёт Chromium browser с помощью Playwright.

```python
@pytest.fixture(scope="session")
def create_browser():
```

Browser работает в режиме:

```python
headless=False
```

то есть браузер визуально открывается во время выполнения тестов.

### `page`

Создаёт новую страницу и открывает:

```text
https://automationexercise.com/
```

После теста страница закрывается.

### `new_user`

Создаёт нового пользователя через UI.

Email генерируется динамически:

```python
new_email = f"test{time.time()}@gmail.com"
```

Это позволяет получать уникального пользователя при каждом запуске теста.

### `register_user_api`

Создаёт пользователя через API.

Преимущество такого подхода — отсутствие необходимости каждый раз выполнять длинный UI-сценарий регистрации.

После теста пользователь автоматически удаляется через API.

# Pytest Markers

В проекте используются собственные Pytest-маркеры.

## `@pytest.mark.critical`

Используется для критически важных тестов.

В проекте этим маркером отмечены, например:

* регистрация пользователя;
* авторизация пользователя.

Пример:

```python
@pytest.mark.critical
def register_user(page):
    ...
```

Запуск только critical-тестов:

```bash
pytest -m critical
```

---

## `@pytest.mark.regression`

Используется для регрессионных тестов.

В проекте данный маркер применяется, например, для проверки добавления товаров в корзину и отдельных тестов пользовательского функционала.

Запуск:

```bash
pytest -m regression
```

---

## `@pytest.mark.dependency`

Используется для построения зависимостей между тестами.

Например:

```python
@pytest.mark.dependency()
def test_login_profile():
    assert True
```

Другие тесты могут зависеть от него:

```python
@pytest.mark.dependency(depends=['test_login_profile'])
def test_view_profile():
    assert True
```

То есть `test_view_profile` и `test_edit_profile` связаны с результатом `test_login_profile`.

---

## Комбинирование маркеров

В проекте также показаны варианты выборочного запуска:

```bash
pytest test_dependency.py -m critical
```

Запуск тестов, кроме regression:

```bash
pytest test_dependency.py -m "not regression"
```

Запуск critical или regression:

```bash
pytest test_dependency.py -m "critical or regression"
```

# Подход к тестовым данным

В проекте используются два подхода к созданию пользователя:

### UI

Пользователь создаётся непосредственно через интерфейс приложения.

Используется для проверки самого сценария регистрации.

### API

Пользователь создаётся через REST API.

Используется как подготовка предусловий для UI-тестов, когда регистрация пользователя не является объектом проверки.

Это позволяет сократить время выполнения тестов и уменьшить количество лишних UI-действий.

# Цели проекта

Основные цели проекта:

* автоматизировать UI-тестирование интернет-магазина;
* автоматизировать тестирование REST API;
* использовать Pytest для организации тестового набора;
* использовать Playwright для browser automation;
* использовать Requests для API;
* применять fixtures для подготовки тестовых данных;
* использовать API для ускорения подготовки предусловий UI-тестов;
* разделять тесты по функциональному назначению;
* использовать Pytest markers для выборочного запуска;
* использовать dependency между тестами там, где порядок выполнения имеет значение.
